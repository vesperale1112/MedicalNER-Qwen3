## 1. 项目目标与总体技术路线

本项目拟构建覆盖精神、行为与神经发育障碍的结构化知识图谱，将分散于 ICD-11、诊断标准、临床指南和循证医学文献中的疾病、症状、诊断要求、风险因素、评估工具、药物与治疗信息组织为具有明确语义和方向约束的知识网络。该知识图谱既可以作为精神疾病知识查询和临床决策支持的基础，也可以作为后续多模态精神疾病识别模型的外部医学知识或结构化先验。

项目采用医学知识设计与计算机实现协同推进的方式。医学团队负责确定疾病覆盖范围、定义节点和关系的临床语义、制定文献检索策略，并对存在医学歧义的知识进行复核；计算机团队负责知识模式的机器可执行化、训练数据构建与清洗、大语言模型微调、实体与关系联合抽取、文献自动筛选、结构校验、语义审计和实验评估。

从计算任务上看，本项目不仅包含狭义的命名实体识别（Named Entity Recognition, NER），还包含实体属性抽取、关系分类、关系方向判断和证据定位。因此，论文中更准确的表述应为“面向知识图谱的实体识别与关系抽取”或“知识图谱结构化信息抽取”。其中，从文本中识别 Disease、Symptom、Medication、Treatment 等节点属于 NER；判断节点间的 `relieved_by`、`assesses_for`、`contributes_to` 等关系则属于关系抽取；为实体补充 ICD 编码、定义、严重程度等信息属于属性抽取。

根据目前已经完成的工作，整体流程可以概括为：

1. 以 ICD-11 精神、行为与神经发育障碍分类体系为疾病知识骨架；
2. 结合临床需求设计实体类型、属性和具有 source-target 方向约束的关系；
3. 从原始疾病资料和医学文本中构建带有实体、关系及证据的训练样本；
4. 使用 Gemini、DeepSeek 等大语言模型辅助生成或修复候选结构化数据，并通过本地规则、WHO ICD-11 API 和人工审计控制质量；
5. 将数据转换为 LLaMA-Factory 可使用的 ShareGPT 格式，对 Qwen3-8B 进行 LoRA/QLoRA 监督微调；
6. 对生成结果进行 JSON、Schema、实体、关系、方向、证据跨度和语义层面的分层评估；
7. 从 PubMed、Embase 和 Cochrane Library 构建治疗相关文章库，使用大语言模型进行全量文献筛选；
8. 将筛选后文章作为药物、治疗、症状缓解、量表评估及风险知识的候选来源，进入后续知识抽取与知识图谱构建环节。

## 2. 医学知识框架与文献来源设计

### 2.1 疾病范围的确定

医学团队对 DSM-5、ICD-10 和 ICD-11 等权威精神障碍分类体系进行了交叉比较。考虑到 ICD-11 是 WHO 最新版通用疾病分类标准，具有疾病覆盖全面、层级清晰、编码规范和临床适配性较强等特点，项目最终以 ICD-11 第 06 章“精神、行为或神经发育障碍”作为疾病实体和分类层级的核心来源。

按照医学部分的论文计划，知识图谱拟覆盖神经发育障碍、精神分裂症及其他原发性精神病性障碍、紧张症、心境障碍、焦虑或恐惧相关障碍、强迫或相关障碍、应激相关障碍、分离障碍、进食或饮食障碍、物质使用或成瘾行为所致障碍、人格障碍、神经认知障碍等 ICD-11 精神疾病类别。采用完整疾病体系而不是只围绕抑郁症建图，有利于支持精神疾病之间的鉴别诊断，并为多模态抑郁症识别提供更完整的疾病边界和外部知识。

### 2.2 概念层与 Schema 设计

医学团队依据临床诊断、鉴别诊断、症状评估、用药和治疗决策流程设计知识图谱节点、属性和关系。计算机团队进一步将这些医学定义转换为可由程序读取和校验的 Schema。

当前 v3.0.0-draft.2 Schema 包含 15 类实体、101 个实体属性和 66 个 active 关系谓词；按照各关系允许的 source 和 target 类型展开后，共形成 96 个 source-target 类型组合。实体类型覆盖 Disease、Symptom、Diagnostic Criterion、Assessment、Patient、Medication、Treatment、Etiology、Risk 等临床知识对象。关系定义不仅包含谓词名称，还明确规定允许的源实体类型和目标实体类型，从而把临床语义转化为可执行的结构约束。

这一设计的重要意义在于，模型不能只生成“语法上像 JSON”的结果，还必须满足医学本体约束。例如，症状与疾病间的关系具有固定方向；药物适应证、禁忌证和副作用的论元类型不能任意互换；研究质量评价工具不能被当作临床 Assessment；一般研究队列的人口学信息也不能自动成为可复用的 Patient Information 知识。Schema 因而同时承担知识组织、模型提示、输出验证和错误过滤四项功能。

### 2.3 医学文献库的来源与检索策略

医学团队采用权威临床指南与前沿循证文献相结合的知识来源体系。指南来源计划包括 Psychiatry Online、美国精神医学学会、英国国家卫生与临床优化研究所、加拿大情绪和焦虑治疗网络及中国相关临床诊疗指南；循证文献主要来自 PubMed、Embase 和 Cochrane Library。

检索策略以 ICD 疾病概念为核心，组合数据库主题词和自由词。PubMed 与 Cochrane Library 主要使用 MeSH，Embase 使用 Emtree；对于缺少直接主题词对应的疾病，采用上位主题词、疾病自由词、历史命名、入口词和下位词进行补充。治疗相关检索进一步加入药物治疗、心理治疗、物理治疗和通用干预术语，并使用数据库提供的治疗副主题词和文献类型过滤条件，重点纳入近十年的系统评价、Meta 分析和随机对照试验。

对于 ICD-11、MeSH 和 Emtree 之间无法严格一一对应的概念，医学团队采用人工语义映射，而不是只依赖字符串相似度。根据概念范围和层级关系，将映射区分为 equivalent、broader、narrower 或不建立对应关系。对于 Cochrane 中容易产生漏检或噪声的疾病，还根据历史病名、欧美诊断体系差异和疾病特异性治疗方式制定个性化检索式，并对高价值综述进行人工复核。

上述内容主要来源于医学团队已经形成的论文材料。检索策略、疾病词表及术语映射的最终数量仍需医学团队在正式论文中补齐，并与计算机团队实际接收的文献文件进行一致性核对。

## 3. 面向知识图谱的大语言模型训练工作

### 3.1 初始训练流水线

计算机团队首先建立了从原始疾病文本到训练数据、模型微调和结果比较的基本流水线。仓库在 2026 年 4 月形成最初的 `kg-lora` 工程结构，主要包括：

- 从原始精神疾病记录中生成带推理过程和结构化结果的候选样本；
- 将生成结果转换为 LLaMA-Factory 使用的 ShareGPT 对话格式；
- 配置 Qwen3-8B 的 LoRA/QLoRA 监督微调；
- 对基础模型和不同 LoRA adapter 的输出进行对比分析；
- 将数据生成、格式转换、训练和评估拆分为可单独运行的脚本，便于调试和重跑。

早期训练数据包含两种生成风格：`specific` 数据强调针对当前文本的具体抽取判断，形成 614 条记录；`standard` 数据采用相对统一的结构模板，形成 635 条记录。随后，计算机团队通过 Gemini 分批生成、断点记录、批次合并和缺失样本补全，将数据扩展为覆盖 858 条疾病记录的完整版本，并保存生成元数据以便追踪数据来源和失败样本。

在早期 5 个样本的基础模型与 LoRA 对比中，基础 Qwen3-8B 去除思考文本后有 4/5 个结果可解析，平均生成 7.0 个实体和 6.25 条关系；`specific` adapter 为 5/5 可解析，平均生成 13.0 个实体和 12.2 条关系；`standard` adapter 同样为 5/5 可解析，平均生成 15.2 个实体和 14.0 条关系。该小样本实验说明 LoRA 微调显著改善了结构格式和抽取覆盖，但不能作为正式准确率：`specific` 模型仍存在关系语义误配，`standard` 模型则更容易过度结构化和引入噪声。

### 3.2 CoT 数据的作用与局限

早期数据同时包含思考过程和最终知识图谱 JSON。614 条 `specific` 数据中有 568 条包含非空 CoT，635 条 `standard` 数据中有 616 条包含非空 CoT。然而，CoT 相对最终 JSON 的长度明显偏短：`specific` 数据的 CoT/输出中位长度比约为 0.15，`standard` 数据约为 0.07。转换为训练对话后，该比例仍分别只有约 0.122 和 0.060。

因此，虽然训练数据并非没有 CoT，但训练损失主要由较长的最终结构化输出贡献。模型推理时往往只生成空的 `<think>` 段，而主要学习到了 JSON 结构。该结果促使后续实验重新讨论训练目标：如果论文目标是提高最终知识图谱抽取质量，则不应为了展示可见推理而保留冗长、噪声较大的 CoT；可以优先采用 output-only 训练，同时通过证据跨度、结构约束和错误分析提供可解释性。

### 3.3 24 GB GPU 上的 QLoRA 基线

计算机团队使用 Qwen3-8B、4-bit QLoRA、LoRA rank 8、batch size 1、梯度累积 8、bf16 和 gradient checkpointing，在单张约 24 GB 的 NVIDIA A10 上进行训练。由于 Qwen3-8B 词表较大，长序列训练时 logits 和损失计算产生较高显存峰值，`cutoff_len=8192` 仍发生 CUDA OOM，最终基线训练只能使用 `cutoff_len=2048`。

完整 858 条样本的 token 长度分析表明，中位总长度为 2,572 tokens，P95 为 7,946，最大值为 20,983。使用 2,048 token 截断时，522/858（60.8%）样本会被截断，而且被截断部分通常位于 assistant response，即 CoT 和最终 KG JSON。这意味着 GPU 基线虽然成功完成训练，但大量样本没有提供完整监督信号。

该基线完成 3 个 epoch、291 个优化步骤，训练耗时约 1 小时 53 分钟，最佳验证损失为 0.6485，对应 checkpoint-280。预测结果的 BLEU-4 为 49.93、ROUGE-1 为 46.52、ROUGE-2 为 29.44、ROUGE-L 为 37.07。需要强调，这些文本生成指标只能反映与参考输出的表面相似度，不能直接代表实体、关系和医学语义的正确性。

### 3.4 昇腾 NPU 长上下文训练

为缓解 24 GB GPU 的长序列显存瓶颈，计算机团队完成了 Qwen3-8B 在昇腾 NPU 环境中的适配，包括训练配置、运行脚本、镜像环境和 FlashAttention 兼容处理。NPU 版本采用 bf16 LoRA、rank 8、alpha 16、全主要线性投影层、batch size 1、梯度累积 8、gradient checkpointing，并将 `cutoff_len` 提升至 16,384。

该实验在 858 条完整 CoT KG 样本上完成 3 个 epoch、291 步训练，总耗时约 1 小时 40 分钟，最佳验证损失为 0.08405，对应 checkpoint-260。与 2,048-token GPU 基线相比，16,384-token 配置能够覆盖几乎全部样本的完整 prompt、CoT 和 KG JSON，从训练数据完整性上显著缓解了截断问题。

在第一轮 20 条生成检查中，BLEU-4 为 48.52，ROUGE-L 为 43.76，严格 JSON 可解析率为 13/20；在包含更多长文本和高复杂度样本的第二轮 20 条结构回归集中，BLEU-4 为 26.54，ROUGE-L 为 33.13，严格 JSON 可解析率下降到 9/20。模型已经能够围绕目标疾病生成实体和关系，较少出现完全跨主题的输出，但长文本仍容易导致重复生成、输出不闭合和属性幻觉。

这组结果表明，将训练 cutoff 提高到 16,384 解决了“训练标签被大量截断”的问题，但没有自动解决自由生成阶段的闭合性和关系语义问题。因此，长上下文容量是必要条件，但不是结构化知识抽取质量的充分条件。

### 3.5 CUDA 与昇腾双后端工作流

为提高训练流程的可复用性，仓库随后将 NVIDIA CUDA 和华为昇腾 NPU 的训练、smoke test 与预测入口统一到可选择后端的运行脚本中，同时保留两个后端各自的模型路径、FlashAttention 处理和输出目录。该设计使同一套数据与 Schema 可以在不同计算平台上复现实验，避免 CUDA 与 NPU 结果相互覆盖，也便于先进行小规模 smoke test，再启动完整训练。

## 4. Schema v2 数据治理与训练数据质量控制

### 4.1 从生成数据到可审计数据

早期大语言模型生成数据存在若干典型问题：历史损坏词、字段不一致、浏览器链接中的合法 `null`、实体类型和关系方向错误、无原文证据的关系、ICD 编码不可靠，以及同一疾病层级的样本可能同时进入训练集和验证集。为了避免将这些问题直接作为监督信号，计算机团队建立了 Schema v2 的确定性迁移和质量审计流程。

该流程遵循“可确定修复、不可确定留痕”的原则：只自动修复可以由文本和规则证明的结构问题；对无法确定的医学语义不静默猜测；所有被拒绝的编码、实体和关系保留审计记录；训练目标只接受 active 关系、合法 source-target 类型以及能够在原文中定位的证据。

### 4.2 WHO ICD-11 校验

项目实现了 WHO ICD-11 MMS API 客户端和结果应用流程，通过 OAuth2 获取访问权限，使用 codeinfo 等接口核对疾病编码、标准名称和 URI。最终 858/858 个主疾病编码均通过 WHO 验证。对非主疾病的历史候选关联，程序记录有效、404、标题不匹配和无需挂接等不同结果，而不是把所有候选编码直接写入训练数据。

主疾病实体统一使用 `icdcode` 属性，并补充 `coding_system`、`icd_release` 和 `icd_uri`。这一工作使疾病身份不再只依赖模型生成的自然语言名称，为后续实体归一化和知识融合提供了权威标识。

### 4.3 证据跨度、关系清洗和数据划分

Schema v2 流程要求关系证据能够精确映射回输入文本。程序对可确定的 evidence offset 进行恢复，并移除没有验证跨度或仍需医学复核的关系。经过迁移、校验和清洗，最终训练就绪语料包含 858 条记录、8,590 个实体和 6,702 条关系；其中 728 条无可靠证据跨度的关系和 182 条 review-only 关系未进入训练目标。

数据被划分为 670 条训练记录、84 条验证记录和 84 条 held-out 记录，另保留 20 条来自同一 858 条源数据的结构回归样本。划分过程检查直接层级和共享父节点，报告的层级泄漏为 0。需要特别说明，20 条结构回归样本并不是独立外部测试集，不能用于报告模型泛化性能。

### 4.4 DeepSeek 辅助语义审计

仓库实现了可恢复的本地 DeepSeek 语义审计阶段，用于对实体判定、关系语义、证据和提示线索进行逐条复核。审计以完整的预清洗数据为输入，任务与数据集版本、记录和关系索引绑定；完成记录不会重复发送，失败记录可以定向续跑。大语言模型只提供受约束的修复建议，本地程序仍需检查 Schema 版本、关系 domain/range、证据文本和输出协议后才能应用。

该阶段的重要方法学边界是：删除无证据关系或通过 JSON 校验并不等于完成医学语义清洗。最终训练前仍需完成 WHO 身份核对、关系修复、训练安全清洗、无泄漏划分、格式转换和严格数据审计。论文中可以将其表述为“大语言模型辅助、确定性验证和人工复核相结合的数据治理机制”，不应表述为由 DeepSeek 自动生成医学金标准。

## 5. 长输出与关系抽取专项实验

### 5.1 长输出不闭合问题

在 `upstream/codex/long-output-cutoff-20260818` 实验分支中，计算机团队针对 Qwen3-8B 的长 JSON 输出问题进行了专项分析。实验使用 1,493 条 DeepSeek teacher 数据，并按照来源组冻结为 1,345 条训练记录和 148 条 held-out 记录，组间重叠为 0。output-only 和 output-priority 两种训练均使用 `cutoff_len=16384`，训练样本的转换后长度未超过该上限。

output-only 模型在 25 条诊断样本中取得 23/25 的 Schema 合法输出，优于基础 Qwen 的 13/25；但仍有样本在生成到 8,192 甚至 16,384 tokens 后没有形成闭合 JSON。结构化停止条件也无法提前终止这些样本，因为模型在触及上限前没有生成第一个完整对象。因此，这类失败不是简单提高 `max_new_tokens` 就能解决，而是模型在长诊断标准文本上持续过生成的问题。

output-priority 方案在限定时间内只完成 6 条诊断样本，其中 4/6 Schema 合法，并表现出更严重的长思考和关系噪声。基于当时证据，output-only 被保留为更合理的主目标，但仍需通过缩短 teacher 输出、增加闭合监督或采用受约束解码改善长输出稳定性。

### 5.2 关系泛化与评估器修正

初始评估曾使用 `(实体类型, 实体名称, ICD 编码)` 共同定义关系端点身份。当模型只预测错中心疾病的 ICD 属性时，所有连接到该中心节点的关系都会被级联判错。例如，某 held-out 样本实际生成了 32/32 条正确关系结构和证据，但中心疾病编码与 teacher 不同，使旧评分器把 32 条关系全部计为错误。

计算机团队因此把评估拆分为实体核心身份、实体属性、核心关系三元组、原始 ID 严格匹配和证据跨度等多个视图。关系端点的核心匹配主要使用归一化后的实体名称和类型，ICD 编码与 span 作为属性单独评分。修正后，16 条配对样本中 checkpoint-500 的 held-out name-aligned relation F1 从旧严格口径的 0.035 提升到 0.737，说明旧指标确实包含明显的级联误判。

不过，评分器修正并没有消除真实模型问题。在更广的 25 条 output-only probe 中，关系 F1 只从约 0.151 提升到 0.177；`diagnosticCriteria` 和 `exclusions` 等字段仍表现出节点类型、关系类型和端点绑定不稳定。进一步检查还发现，1,493 条数据中有 702 条 teacher 目标包含学生输入中没有出现的 ICD 编码，267 条输入缺少规范标题。这说明部分低分来自 teacher 拥有学生不可见的特权信息，属于数据转换和输入可识别性问题。

该实验最终将问题定位为三部分：长字段上的生成不闭合、特定字段的关系绑定不稳定，以及 teacher/student 输入信息不一致。它不能被简单概括为“模型过拟合”或“模型能力不足”。

### 5.3 relations_v2 output-only 再训练

在 `upstream/codex/relations-v2-code-20260825` 分支中，计算机团队根据医学团队复核后的关系表进一步构建 `relations_v2` 训练流程。该流程冻结 active 关系词表和 source-target 约束，压缩 JSON，只训练最终结构化输出，并将包含关系的训练记录过采样一次，以缓解大量实体 token 对关系监督的稀释。

训练使用 Qwen3-8B、LoRA rank 8、全部线性模块、bf16、batch size 1、梯度累积 8、3 个 epoch 和 `cutoff_len=16384`。过采样后训练集为 2,183 条，开发集为 148 条；训练与验证样本最大组合长度分别为 8,657 和 8,951 tokens，均未超过 cutoff。训练共完成 819/819 步，最佳 checkpoint 为 checkpoint-750，最佳验证损失为 0.03482，最终训练损失为 0.03431。

训练后开发集 probe 共 8 条，6/8 输出闭合；两个 `diagnosticCriteria` 样本生成到 16,384 tokens 后仍为 invalid JSON。训练集 probe 为 6/6 闭合。按 core triple 口径，开发集 relation F1 为 0.061，训练集为 0.579；按 relation type 单独计算，开发集和训练集分别约为 0.306 和 0.621。这些指标以 DeepSeek teacher 为参照，不是人工医学金标准，但表明开发集上的关系绑定泛化和长诊断标准过生成仍未解决。

因此，`relations_v2` 分支证明了以下几点：关系协议可以被整理为可训练的 closed vocabulary；完整训练和远程快照机制已经跑通；仅凭较低 eval loss 不能选择医学上最好的 checkpoint；关系类型、端点绑定、实体属性和输出闭合应作为独立指标报告。

## 6. 治疗相关文章的自动筛选工作

### 6.0 三库原始文献的抽取、清洗与库内去重

在进行大语言模型筛选前，计算机团队首先实现了 PubMed、Embase 和 Cochrane Library 三种不同导出格式的统一解析程序。程序分别读取 PubMed 文本块及其 PMID 元数据、Embase 紧凑字段导出和 Cochrane CSV，将结果统一为 `source`、`disease_codes`、`doi`、`title` 和 `abstract` 等字段。

清洗过程对 HTML 实体、Unicode NFC、换行符、不间断空格和摘要前缀进行规范化，但不改写医学内容。空摘要不作为可筛选记录输出；同一文章在多个疾病检索式中出现时，其疾病代码被合并为多标签。由于三种数据库可用标识不同，去重身份也按来源区分：PubMed 使用 PMID，Cochrane 使用 Cochrane Review ID 或 CENTRAL ID，Embase 在有 DOI 时使用规范化 DOI 与标题，在无 DOI 时使用规范化标题与清洗后摘要内容标识。当前去重只在各数据库内部进行，没有把跨 PubMed、Embase 和 Cochrane 的相似记录强行合并。

当同一来源和同一身份的记录存在多个摘要版本时，程序保留清洗后更长的摘要，同时记录内容冲突、替换次数、备选标题、备选标识和全部来源文件。处理使用有界线程池并保持确定性输出顺序，大型 `records` 数组以流式方式写入临时文件后再替换正式输出，避免在内存中构造第二份完整语料。

最终 `articles.json` 的来源级处理统计如下：

| 来源 | 读入记录 | 跳过空摘要 | 库内重复记录 | 内容冲突 | 以更长摘要替换 | 最终唯一记录 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| PubMed | 241,025 | 1,303 | 115,921 | 50 | 11 | 123,801 |
| Embase | 227,255 | 2,193 | 97,157 | 776 | 149 | 127,905 |
| Cochrane | 1,262 | 0 | 466 | 16 | 7 | 796 |
| 合计 | **469,542** | **3,496** | **213,544** | **842** | **167** | **252,502** |

PubMed 的 123,801 条记录全部以数据库原生 ID 识别；Embase 中 101,155 条使用 DOI+title，26,750 条使用 title+abstract；Cochrane 的 796 条均使用数据库原生 ID。该统计能够解释为什么早期方案文档中的语料规模约为 180,373，而最终正式语料扩展到 252,502：检索文件、抽取逻辑和最终输入快照在项目推进中发生了更新。论文应使用最终语料数字，同时把早期 180,373 条写成方案设计阶段的历史快照，而不是与最终数字并列为同一批数据。

### 6.1 从小样本验证到正式筛选任务

为了把医学团队检索得到的大规模文献转化为适合知识图谱抽取的候选集合，计算机团队首先构建了 22 条治疗相关文章测试集，用于比较本地微调 Qwen3 模型和外部大语言模型的生成结果。测试数据被转换为 ShareGPT/LLaMA-Factory 格式，并保留文章来源、原始索引、标题和摘要长度等 manifest 信息。随后使用 Gemini 对 22 条样本进行结构化生成，并建立 checkpoint、失败详情和本地规范化机制，以验证外部模型处理治疗摘要的可行性。

早期实践表明，直接让模型完成完整 KG 抽取容易受到输出格式、关系命名和长文本的影响；而使用低质量模型先做不可逆筛选又可能丢失有价值文章。因此，项目将第一阶段明确为“高召回文献筛选”：模型判断文章是否包含当前 Schema 可表达的、具有原文证据的可复用知识，并给出少量候选关系或属性，而不是直接生成完整知识图谱。

### 6.2 筛选标准与提示词演化

筛选任务采用 KEEP、REVIEW、DROP 三分类：

- KEEP：文章中存在至少一个可由当前 Schema 表达、具有直接证据且具有复用价值的关系或高价值属性；
- REVIEW：文章可能包含相关知识，但实体类型、关系方向、证据完整性或语义泛化存在歧义，需要进一步复核；
- DROP：标题和摘要中没有可进入当前知识图谱的关系或高价值属性。

提示词经历了“关系优先”“任意属性也可保留”和“关系优先 + 高价值属性例外”等版本比较。最终采用混合策略：逐句优先扫描 active 关系，同时允许药物适应证、明确副作用、疾病定义、核心表现和风险警示等可复用属性触发 KEEP；研究队列中的单个年龄、样本性别、入组条件和个体病史等仅描述本研究人群的信息不能单独触发 KEEP。

模型输出同时包含 decision、reason、最多三个候选事实、实体类型、关系或属性名称及 exact evidence quote。证据必须是标题或摘要中的连续原文片段，禁止使用省略号拼接、改写或补充外部知识。程序进一步检查 JSON 字段、Schema 中的实体类型和关系、source-target 组合以及证据是否真实包含于原文。

在 50 条对齐样本的早期比较中，团队同时测试了 GPT-5.4 mini、GPT-5.4、GPT-5.6 Luna、GPT-5.6 Sol 和人工判断，发现不同模型在召回、精确性和格式稳定性间存在明显取舍。因此，最终没有只依据单一模型或单一准确率确定筛选器，而是优先保护 DROP 召回，并通过后续人工抽样持续修订边界规则。

### 6.3 可恢复的全量筛选程序

计算机团队为 252,502 篇文章加入连续的零起始索引 `0..252501`，并以索引而不是标题作为唯一处理键，避免重复标题导致结果覆盖。正式 runner 支持：

- 按 `--start-index` 和包含式 `--end-index` 选择文章范围；
- 使用多个 worker 并按照 `index % workers` 稳定分配任务；
- 每次尝试追加写入 JSONL checkpoint；
- 依据每个索引的最新 attempt 判断状态；
- 已完成文章自动跳过，指定失败类型可定向重试；
- 在不调用付费 API 的 preview 模式下检查选中范围、待请求数量和 worker 分配；
- 对大体积 `articles.json` 使用索引定位和区间读取，避免每次为小范围任务顺序扫描完整文件；
- 最终按索引生成独立的结果 JSON，同时保留 checkpoint 中的模型、Schema、原始输出、token usage 和重试历史。

为避免上游服务暂时不可用造成失败记录污染，后期 runner 不再将瞬时 `request_failed` 写入 checkpoint，使缺失索引在下一次扫描时自然重试；JSON 解析失败、Schema 失败和证据失败仍保留，用于诊断模型输出。最终还增加了针对格式失败和特定验证错误的精细化重试逻辑。

### 6.4 大文件读取和 checkpoint 优化

原始文章文件约 587 MB，完整 checkpoint 最终达到约 447 MB。为降低小范围试跑的启动时间，程序实现文章记录计数、索引偏移定位和区间迭代读取。对 `50000..50049` 的 50 条范围，二分定位读取约 0.039 秒，而顺序扫描曾约为 28.5 秒。

不过，大规模 checkpoint 的重新载入仍然是本地耗时来源。runner 在 worker 完成后会再次读取完整 append-only JSONL 以构建最终状态，最终输出构建还可能再次遍历 checkpoint。因此，API 请求结束后到最终统计显示之间的等待主要是本地 I/O 和 JSON 解析，而不是隐藏的 API 调用。该问题已经完成定位，但当前主线尚未把所有后处理改成完全复用内存状态。

### 6.5 Schema v2、v3 与多模型并行演进

前 50,000 篇文章使用 GPT-5.6 Luna 和 v2.0.0-draft.2 Schema；随后 7,708 条最新结果使用 GPT-5.6 Luna 和 v3.0.0-draft.1；其余 197,197 条最新结果主要使用 Gemini 3.7 Flash 和 v3.0.0-draft.2。为了节约已经发生的付费调用，runner 允许旧版本结果继续保留，而不是在每次提示词或 Schema 更新后强制重新处理所有文章。

这种策略降低了计算和 API 成本，但使最终 checkpoint 成为多模型、多 Schema 世代的混合数据。下游必须以每个索引最新 attempt 中的 `model` 和 `output.schema_version` 作为 provenance，不能只读取 checkpoint 文件名或首行 metadata。论文中应明确说明不同世代的筛选结果不能被当作同一模型、同一提示词上的纵向准确率曲线。

## 7. 文献筛选最终结果与质量审计

### 7.1 全量技术结果

截至 2026 年 9 月 1 日，252,502 个文章索引均已有最新 completed 结果，最终 JSON 与 checkpoint 中每个索引的最新输出逐条比较后差异为 0。最终决策分布如下：

| 数据来源 | KEEP | REVIEW | DROP | 合计 |
| --- | ---: | ---: | ---: | ---: |
| Cochrane | 648 | 10 | 138 | 796 |
| Embase | 70,732 | 3,522 | 53,651 | 127,905 |
| PubMed | 65,461 | 5,043 | 53,297 | 123,801 |
| 合计 | **136,841** | **8,575** | **107,086** | **252,502** |

KEEP 与 REVIEW 合计 145,416 篇，占全量文章的 57.59%。checkpoint 共保存 256,595 条 attempt，其中 4,093 条旧记录被后续 attempt 覆盖。最终 JSON 只保留排序后的最新 `{index, output}`，适合下游读取；完整 checkpoint 则保留 provenance、原始回答、usage、错误和重试历史，应继续保存以支持审计。

### 7.2 格式恢复与定向重试

全量首次完成时有 205,557 条输出直接通过验证，46,945 条为 `completed_with_validation_errors`。其中绝大部分并非语义错误，而是 Gemini 在合法 JSON 外增加了 Markdown JSON 围栏。第一次本地去除标准围栏后，invalid 从 46,945 降至 3,571，避免了对 43,374 条已付费结果的重复调用。

对剩余失败记录进行多轮定向重试和再次本地恢复后，最后 39 条被逐条处理。其中包括标准围栏、原始数据中的反斜杠转义、大小写差异以及 8 条需要人工判断的真实问题。最终所有 252,502 条结果在结构和证据验证层面均达到 completed。

这项工作形成了明确的错误处理层级：标准代码围栏等可证明等价的包装问题优先本地恢复；网络故障等待服务恢复后重试；真实 Schema 或证据错误保留并定向处理；无法由字符等价证明的内容不能仅通过修改状态变成 valid。

### 7.3 Luna/v2 前 50,000 篇审计

前 50,000 篇 Luna/v2 输出中，47,597 条严格验证通过，2,301 条完成但验证失败，99 条 JSON 解析失败，3 条 API 请求失败。计算机团队使用固定种子 `20260804`，将 `0..49999` 分为五个连续区间，每个区间抽取 30 条 DROP、20 条 KEEP 和 5 条 REVIEW，共人工复核 275 条。

在 150 条模型 DROP 中，116 条维持 DROP，18 条应改为 KEEP，16 条至少应为 REVIEW，即 34/150（22.7%）不适合被不可逆删除。在 100 条 KEEP 中，92 条维持 KEEP、4 条改为 REVIEW、4 条改为 DROP；如果只判断是否保留，96/100 仍应保留。25 条 REVIEW 中，21 条维持 REVIEW、4 条可提升为 KEEP，没有样本应明确 DROP。

最稳定的漏检模式是模型把量表、问卷和评分工具视为“只是试验结局”，从而遗漏 `assesses_for` 等关系。因此，结构验证通过并不能发现关系漏抽，DROP 也不能直接作为永久删除依据。

### 7.4 Luna/v3 小规模试跑

在正式扩展 v3 前，团队对索引 `50000..50049` 的 50 篇文章进行了连续试跑和逐条复核。模型决策与人工精确一致 44/50（88.0%），保留/过滤方向一致 46/50（92.0%）。主要问题包括 Etiology 与 Risk 混淆、把 Newcastle-Ottawa Scale 等研究质量工具识别为临床 Assessment，以及将一般 `Evidence.study_type` 当作足以 KEEP 的高价值属性。5 条格式失败均涉及不连续或被改写的 evidence quote。

该试跑说明，在投入更大规模调用前同时检查提示词、Schema、实体类型、关系方向和证据跨度，可以提前发现系统性错误；同时，50 条试跑结果仍不足以证明全量语义准确率。

### 7.5 Gemini/v3 分层语义审计

2026 年 8 月 25 日的混合 checkpoint 审计按来源、模型、Schema 和 decision 分层抽取 55 条记录。25 条 Gemini/Embase DROP 经人工复核后，12 条应 KEEP、4 条应 REVIEW，仅 9 条维持 DROP。主要错误是模型把 RCT 或 Meta 分析中的治疗效果视为普通研究结局，遗漏明确的 `Symptom relieved_by Treatment/Medication` 关系。

基于该结果，筛选 prompt 增加了精简的对称边界：试验目的不能自动成为推荐或适应证，但原文直接报告治疗或药物缓解某一症状时，可以支持 `relieved_by`；研究质量工具不是临床量表；明确的用药用途与一般研究设计需要区分。修改保持简短，以避免提示词膨胀反而干扰模型。

在 2026 年 9 月 1 日的最终新抽样中，团队只从最新 Gemini/v3.0.0-draft.2 记录中抽取 Embase 20 条和 PubMed 20 条。20 条模型 DROP 中，6 条应 KEEP、4 条应 REVIEW、10 条维持 DROP；16 条 KEEP 全部维持 KEEP，4 条 REVIEW 全部维持 REVIEW。该样本有意提高 DROP 比例，不能作为全量自然准确率，但再次证明 DROP 漏召回同时存在于 Embase 和 PubMed。

### 7.6 候选事实层面的风险

即使文章的 KEEP/REVIEW/DROP 决策正确，模型给出的候选事实也可能存在以下问题：

- 将研究目的或试验药物错误泛化为既定适应证；
- 将小样本观察到的不良事件泛化为药物通用副作用；
- 混淆 Etiology 与 Risk；
- 将研究质量评价工具当作临床量表；
- 使用 `intervention` 等泛称或代词作为关系论元；
- 将机构名称而不是具体指南文档标记为 Guideline；
- 关系方向正确但实体名称不够自包含，无法直接复用；
- 原文中存在相关事实，但模型完全漏掉，格式 validator 无法发现。

因此，KEEP 可以用于文章保留，但候选事实进入正式知识图谱前仍需 candidate-level validation，包括实体语义、关系方向、论元可识别性、证据自包含性和跨研究泛化合理性检查。

### 7.7 盲审工具

为了支持专家在不受模型答案影响的情况下评估筛选质量，计算机团队制作了可离线分享的 40 篇文章盲审页面。样本在模型和 KEEP/NON_KEEP 间分层平衡，页面默认隐藏模型答案，支持专家独立选择 KEEP、REVIEW 或 DROP、填写备注、在浏览器本地自动保存进度并导出 JSON。该工具可以作为后续构建正式人工 gold set 的原型。

## 8. 医学与计算机工作的衔接方式

### 8.1 概念层

医学团队以 ICD-11、诊断要求、临床指南和专家经验定义疾病范围、节点属性和关系语义；计算机团队将其转换为版本化 Schema，并把 source-target 类型、关系方向、属性字段和状态写成可执行协议。对于有争议的关系，不由程序自行决定医学含义，而是进入医学复核队列。

### 8.2 数据层

医学文本首先经过结构和字符层面的确定性清洗，再由大语言模型辅助生成实体、关系和证据候选。WHO API 用于疾病编码和标准身份校验，本地 validator 用于 JSON、Schema、方向与证据检查，人工或受约束的大语言模型审计用于识别规则无法发现的语义问题。最终只有满足训练门槛的数据进入 Qwen3 微调。

### 8.3 模型层

Qwen3-8B 通过 LoRA/QLoRA 学习从医学文本生成结构化实体和关系。CUDA 和昇腾 NPU 双后端支持训练与预测，长上下文配置提高完整监督覆盖。模型评估从早期 BLEU/ROUGE 逐步扩展为 JSON 闭合、Schema 合法率、实体 F1、关系 F1、方向、端点绑定、属性和证据跨度等结构化指标。

### 8.4 文献层

医学团队的检索策略保证候选文献来源和检索式具有临床合理性；计算机团队通过大语言模型对 252,502 篇标题和摘要进行高召回筛选，并通过 checkpoint、精细重试、格式恢复和分层语义审计保证流程可恢复、结果可追踪。筛选的主要作用是降低后续完整知识抽取和专家复核的优先级成本，而不是直接把 DROP 文章永久删除。

### 8.5 图谱构建层

按照论文计划，筛选后的高价值文献将与 ICD-11 诊断知识、临床指南共同进入知识抽取和融合阶段。实体经过标准化和消歧，关系必须满足 Schema 方向与证据约束，最终合法三元组再进入图数据库。Neo4j 可视化、语义查询、辅助诊断和风险预警目前在本仓库中尚未发现完整实现，现阶段应作为下一阶段图谱应用计划描述。

## 9. 可用于论文 Methods 的写作框架

### 9.1 Concept layer design

本研究采用自上而下的知识图谱构建策略。医学团队以 ICD-11 精神、行为与神经发育障碍分类体系为疾病骨架，结合临床诊断要求、精神科指南和临床使用场景，定义疾病、症状、诊断标准、评估工具、患者信息、病因、风险因素、药物和治疗等实体类型。每类实体配置相应属性，每条关系明确谓词、源实体类型、目标实体类型和语义说明。计算机团队将医学定义转换为版本化、机器可执行的 JSON/CSV Schema，用于约束训练数据、模型提示和输出验证。

### 9.2 Training-data construction and quality control

原始疾病文本首先由大语言模型辅助生成实体、关系和证据候选，随后转换为统一结构。确定性程序修复可证明的字符和字段错误，并要求关系证据与原文精确对应。疾病编码通过 WHO ICD-11 MMS API 进行身份核对；不满足证据、关系方向或 active Schema 的候选被移出训练目标并保留审计记录。数据按照疾病来源组和层级关系划分为训练、验证和 held-out 集，以降低相近疾病进入不同数据集造成的信息泄漏。

### 9.3 Model training

本研究使用 Qwen3-8B 作为基础模型，通过 LLaMA-Factory 实施 LoRA/QLoRA 监督微调。训练目标为从医学文本生成包含实体和关系的结构化 JSON。早期实验比较 specific-CoT、standard-CoT 和完整 858 条疾病数据，并分别在 NVIDIA GPU 和华为昇腾 NPU 上建立训练流程。针对长文本截断和冗长推理问题，后续实验采用 output-only 目标、16,384-token 上下文和分组隔离的验证集，同时对关系样本进行针对性评估。

### 9.4 Literature screening

治疗文献来自 PubMed、Embase 和 Cochrane Library。筛选模型读取标题与摘要，根据当前 Schema 判断其中是否包含可复用的实体关系或高价值属性，并输出 KEEP、REVIEW 或 DROP、判断理由、候选事实和连续原文证据。筛选程序使用唯一文章索引、并发 worker、append-only checkpoint 和版本化 provenance 支持全量运行与失败恢复。输出先进行结构和证据验证，再通过来源、模型、Schema 和决策分层的人工抽样评估语义质量。

### 9.5 Evaluation

模型与数据质量采用分层评价。数据层检查字段完整性、ICD 身份、Schema 合法性、关系方向、证据跨度和数据划分泄漏；生成层检查 JSON 闭合率、Schema 合法率、实体核心身份、实体属性、关系三元组、关系类型、端点和证据；文献筛选层分别报告精确决策一致性、保留/过滤一致性和不同决策类别的人工复核矩阵。由于 DeepSeek/Gemini teacher 和单人审计均不构成正式金标准，相关结果只作为工程质量和风险证据，正式准确率需要独立双人标注并仲裁的数据集。

## 11. 项目的阶段性创新点

### 11.1 以临床关系约束驱动知识抽取

项目没有把知识图谱抽取简化为无约束实体识别，而是把医学团队定义的 source-target 关系方向编译成模型提示和 validator。该设计能够在生成后过滤实体类型和关系方向不符合临床逻辑的三元组，并把错误定位到具体 relation 和端点。

### 11.2 将权威疾病身份与生成模型解耦

疾病名称和 ICD 编码不完全依赖大语言模型记忆，而是使用 WHO ICD-11 MMS API 核对主疾病身份。模型主要负责从文本中识别候选结构，权威外部资源负责标准编码和 URI，从而降低生成模型在疾病规范化上的幻觉风险。

### 11.3 建立可审计、可恢复的训练和筛选流程

数据生成、语义审计和文献筛选均采用 checkpoint 或 manifest 保存来源与处理状态。付费 API 失败可以定向续跑，已完成记录不会重复请求；格式包装问题优先本地恢复；模型、Schema 和重试历史保留在 append-only checkpoint 中。该设计增强了大规模医学文本处理的可追溯性。

### 11.4 从文本生成指标转向 KG 结构指标

项目早期使用 BLEU/ROUGE 观察生成结果，后续发现这些指标无法识别关系方向、实体属性和证据错误，因而建立多视图实体与关系评分。尤其是将实体核心身份与 ICD/span 属性分开，避免单个属性错误级联为全部关系错误。这一评估修正对结构化医学信息抽取具有直接方法学价值。

### 11.5 将结构有效性与语义有效性分开报告

无论是训练数据还是 252,502 篇筛选结果，项目均明确区分 JSON/Schema/证据验证与医学语义正确性。格式验证用于排除可自动发现的错误，人工分层审计用于发现漏抽、过度泛化和类型混淆。该区分避免把“程序可以读取”误写成“医学内容准确”。

## 12. 局限性与正式论文中不能过度声称的内容

1. 当前多数语义审计由单人完成，尚未建立双人独立标注、分歧仲裁和正式一致性指标，不能将抽样结果称为金标准准确率。
2. 早期 5 条、20 条和部分 8/16/25 条 probe 的样本量较小，主要用于工程诊断，不能代表全部精神疾病文本。
3. 训练数据中的 Gemini 或 DeepSeek 输出是 teacher reference，不等同于医学专家标注；模型与 teacher 的一致性也不等同于医学正确性。
4. 不同阶段使用 614/635、858、1,493 和过采样后的 2,183 条训练记录，数据来源和训练目标不同，不能直接比较 loss 或 F1。
5. 文献筛选结果混合 GPT-5.6 Luna 与 Gemini 3.7 Flash，以及 v2、v3 draft.1 和 v3 draft.2 三个 Schema 世代；下游需要分版本处理或显式迁移。
6. 全量筛选达到 100% completed 和结构验证通过，只说明技术流程闭环，不表示语义准确率为 100%。
7. DROP 在多轮人工抽样中均表现出漏召回风险，不适合直接永久删除；它更适合作为低优先级队列。
8. KEEP 决策正确不表示其候选关系一定可以直接入图，仍需候选事实级语义校验和知识融合。
9. 当前仓库尚未提供完整 BRAT/BIO 标注流程、传统 NER 基线、Neo4j 入库与临床应用系统的实现证据，这些内容只能作为计划或待补充的外部工作。
10. 当前图谱模型主要处理文本知识，尚未完成与影像、语音、量表时序数据等多模态信息的正式融合。

### 17.1 Gemini 生成过程的恢复机制

Gemini Pro 生成早期受到每日配额限制。2026 年 4 月 30 日的快照中，索引 1—471 只有 456 条成功，程序明确列出缺失索引并建议按小块续跑。每个阶段检查重复 `global_idx`、空 CoT、空输出、非法关系端点及异常字符，并在转换为 LLaMA-Factory 格式时报告跳过数量。到 2026 年 5 月 7 日，Pro COT long_text 和 Flash structure 都覆盖了 858 条记录；Pro structure 当时仍为 449/858，受配额限制。

这些记录说明数据构建并非一次性调用，而是经历了分片生成、状态恢复、缺失索引定位、批次合并、版本归档和最终完整性检查。论文方法中可以概括为“分片式、可恢复的 teacher 数据生成流程”，详细 quota 信息可放补充材料。

### 17.2 Schema v2 迁移的中间状态

Schema v2 的首次迁移对 858 条输入实现无静默丢失和幂等处理。迁移报告记录了 72 次损坏文本修复、858 次源身份挂接、16,442 次属性重命名、858 次主疾病编码注入、485 条有文本依据的 Patient-to-Disease 关系添加、4,577 次关系证据跨度补充、181 次关系改写、3 个描述子节点折叠和 16 次规范主疾病注入。

迁移完成后，618 条记录直接标记 repaired，240 条进入 manual_review；结构校验没有 error，但 96 条记录中的 182 条关系带有“需要医学复核”的 warning。应用 WHO 结果后，858 个 canonical main disease 全部 verified；非主疾病候选中 72 个明确无效、256 个标题不匹配、406 个有效但不属于最终主疾病编码合同，因此均没有直接挂接到训练目标。

训练 sanitizer 最终删除 90 个实体、728 条无 verified span 的关系和 182 条需要医学复核的关系，同时清除 10,293 个 legacy 字段。处理后 858 条记录全部为 repaired，严格训练审计中的 JSON、Schema、主疾病身份、ICD 验证、active relation、exact span、已知损坏词、训练资格和 split integrity 等 gate 全部通过。

## 18. 当前 v3 Schema 的完整实体与关系范围

### 18.1 15 类实体及属性

1. **Disease**：ICD 编码、DSM-5 映射、定义、亚型、specifier、严重程度、病程、流行病学和预后。
2. **Symptom**：名称、描述、类别、父症状、严重程度、持续时间、频率、敏感度、特异度和风险因素。
3. **Diagnostic Criterion**：来源、criterion ID、描述、是否必需、逻辑和阈值。
4. **Assessment**：评估类型、问题、触发条件、追问和用途。
5. **Patient**：年龄、性别、职业、教育、婚姻、家族史、精神病史、创伤、物质使用和特殊人群。
6. **Medication**：通用名、ATC 编码、机制、剂量、适应证、禁忌证、副作用、相互作用、代谢、妊娠和哺乳信息。
7. **Treatment**：治疗类型、描述、机制、适应证、禁忌证、持续时间、频率和证据等级。
8. **Treatment Plan**：方案名称、适用疾病、疾病阶段、严重程度、目标人群、推荐等级和描述。
9. **Examination**：检查类型、描述、用途和结果解释。
10. **Assessment Scale**：量表名称、cutoff、分数范围、解释和目标疾病。
11. **Etiology**：病因类型、描述和证据。
12. **Risk**：风险类型、风险等级、描述、证据等级、增险因素、保护因素和警报触发条件。
13. **Communication Strategy**：沟通策略、场景、目标人群、禁忌、适用阶段和家庭支持要求。
14. **Guideline**：指南名称、发布机构、版本和发表年份。
15. **Evidence**：PMID、DOI、研究类型、期刊、证据等级和发表年份。

### 18.3 需要继续医学确认的 Schema 问题

完整关系表的存在并不表示每条关系已经具备同等强度的医学共识。历史审计曾发现：部分关系名称需要重命名；同一谓词可能跨不同 source module 复用；关系表中的 source 是医学模块还是实际 node label 需要统一；`belongs_to`、因果关系、禁忌/副作用和强 `confirms` 语义仍可能需要医学复核。正式论文应以最终冻结版本为准，并报告版本号与冻结日期。

### 19.2 为什么不能只用 loss 选择 checkpoint

长输出分支的 output-only checkpoint-350、400、450 和 500 在 token-level loss 上都已经很低，但生成行为并不单调改善。checkpoint-350/400 有明显截断或格式失败；checkpoint-450/500 的结构闭合更好，但不同字段上的 relation 表现差异很大。旧 code-sensitive scorer 又会将中心疾病属性错误传播到全部关系。因此，最低 eval loss 不能直接代表最佳实体关系抽取质量。

后续 checkpoint 选择至少应同时考虑：Schema 合法率、JSON 闭合、实体 core F1、属性 F1、name-aligned relation F1、relation type F1、证据一致性、分字段表现和人工医学审计。若目标是部署，还需加入生成时延和最大 token 命中率。

### 19.3 长字段的错误分布

当前最困难的字段不是均匀分布的。`indexTerms` 一类规则性较强的关系链可以在训练和 held-out 中复现；`diagnosticCriteria` 容易把长诊断标准片段错误分类为 Symptom，并生成错误的 `is_core_symptom_of`、`is_associated_symptom_of` 或其他关系；`exclusions` 的关系方向和是否应建边也不稳定；`definition` 有时生成原文支持但 teacher 未标注的额外关系，不能在没有人工 policy 的情况下全部称为 hallucination。

这说明下一轮数据建设应按 source field 分桶，而不是继续无差别增加样本或 epoch。对于 Diagnostic Criterion，需要明确长段落节点边界和与 Disease 的固定关系；对于 exclusions，需要统一“排除性诊断条件”与一般鉴别疾病的表达；对于 definition，应先确定高召回或高精确的标注政策。

## 20. 文献筛选决策的演进与证据

### 20.1 最初方案与最终实现的差异

早期方案曾建议由前沿模型对约 18 万篇去重摘要执行一次 extract-or-abstain：能提取证据绑定关系时返回简洁图谱，不能提取时返回空图谱；不采用能力较弱的模型先筛选，以免产生不可恢复的误删。该方案还提出跨数据库去重、供应商原生 Batch API、prompt caching、多摘要 packing 试验和关系级二次验证。

最终主线选择了更轻量的 KEEP/REVIEW/DROP 筛选任务，而不是直接对全部文章生成完整图谱。这个变化降低了每篇文章的输出长度和 Schema 负担，但也引入新的边界问题：模型需要判断哪些事实值得保留，DROP 漏召回因此成为关键风险。跨来源去重、原生 Batch API、多摘要 packing 和全量关系级复核目前仍属于计划，没有作为已完成结果写入。

### 20.2 五方 50 篇模型比较

同一批 50 篇文章由人工初审、GPT-5.4 mini、GPT-5.4、GPT-5.6 Luna 和 GPT-5.6 Sol 判断。以人工初审的 21 篇应保留文章为参照：

| 模型 | 三分类一致率 | Cohen's kappa | 保留 Precision | 保留 Recall | 保留 F1 | 误删 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPT-5.4 mini | 58.0% | 0.189 | 55.6% | 47.6% | 51.3% | 11 |
| GPT-5.4 | 72.0% | 0.482 | 73.7% | 66.7% | 70.0% | 7 |
| GPT-5.6 Luna | 72.0% | 0.452 | 80.0% | 57.1% | 66.7% | 9 |
| GPT-5.6 Sol | 66.0% | 0.444 | 63.3% | 90.5% | 74.5% | 2 |

Sol 没有过滤任何人工明确 KEEP，其两个误删均为人工 REVIEW 的成像工具边界样本；GPT-5.4 的三分类一致率和 kappa 较高；Luna 精确率较高但召回不足；mini 同时存在低召回和 7 条格式错误。该比较支持“召回优先时使用更强模型或保留 REVIEW，不能由 Luna/mini 单独不可逆删除”的结论。

四个 API 模型处理 50 篇文章的 total token 大约在 99,166—102,128 之间；运行时间从 GPT-5.4 mini 的 230.6 秒到 GPT-5.6 Sol 的 687.1 秒不等。该数据只反映当次服务和墙钟时间，不代表固定模型价格或稳定吞吐。

### 20.3 Prompt 边界逐步明确的内容

1. 关系优先：文章至少应有一个 Schema 可表达关系，或有明确的高价值可复用属性。
2. 队列信息限制：单个年龄、性别比例、入组标准和当前样本用药史不能单独触发 KEEP。
3. 量表规则：量表作为 RCT outcome 或 eligibility measure 时仍可能支持 `assesses_for`、`evaluates` 或 `measures`；研究质量工具不属于临床 Assessment Scale。
4. 风险规则：环境暴露和危险因素应建模为 Etiology；明确增加疾病发生风险时可使用 `Etiology -> contributes_to -> Disease`，不能随意改成预后关系。
5. 治疗效果规则：RCT/Meta-analysis 的一般存在不自动产生推荐，但原文明确报告某 Treatment/Medication 缓解某 Symptom 时可支持 `relieved_by`。
6. 用途与适应证规则：试验“正在评估”某药不能自动证明适应证；明确“used to treat”“first-line”或指南推荐才可形成相应事实。
7. 证据规则：evidence quote 必须为连续原文，不允许省略号拼接、缩写改写或从标题和摘要的不同位置组合。
8. 继续扫描：发现一个属性后不能停止，仍需检查全文其他句子中的关系，尤其是量表和症状缓解。

### 20.4 验证器可以和不可以发现的错误

| 错误类型 | 自动验证能力 | 后续处理 |
| --- | --- | --- |
| 非法 JSON、字段缺失、字段类型错误 | 可以 | 本地恢复或定向重试 |
| 非 Schema 实体/关系 | 可以 | 判 validation error |
| source-target 类型组合非法 | 可以 | 判 validation error |
| evidence 不在原文、非连续或大小写不符 | 多数可以 | 区分真实改写与上游字符差异 |
| Markdown JSON 围栏 | 可以识别为包装失败 | 仅剥离标准围栏后重新完整验证 |
| 量表关系漏抽 | 不可以 | 人工/第二模型语义审计 |
| 治疗效果漏抽 | 不可以 | 人工/规则救援/第二模型复核 |
| 试验目的被当作适应证 | 不可以 | candidate-level 语义校验 |
| 单研究副作用被过度泛化 | 不可以 | 检查研究设计与表述强度 |
| Etiology/Risk 语义混淆 | 通常不可以 | 医学语义复核 |
| 泛称或代词作为论元 | 通常不可以 | 自包含性检查和实体规范化 |
| 完全未输出潜在事实 | 不可以 | 对 DROP/空结果做分层召回审计 |

## 22. 负结果、被否决方案与形成的经验

1. **单张 24 GB GPU + 8B + 长上下文不可直接解决。** 4-bit 权重量化并不能消除长序列 logits/loss 的显存峰值；普通 DDP 也不一定解决单卡 activation 问题。
2. **仅提高 cutoff 或生成上限不够。** 训练数据不再截断后，模型仍可能在推理时重复生成到 16,384 tokens 而不闭合。
3. **BLEU/ROUGE 不等于 KG 质量。** 文本相似度较高时仍可能关系方向错误、实体属性幻觉或 JSON 不闭合。
4. **CoT 不是天然更好。** CoT 监督相对 JSON 太弱时不会保留可见 reasoning；冗长或噪声 CoT 还会占用上下文和生成预算。
5. **更低 loss 不等于更好关系泛化。** checkpoint 选择必须结合结构化生成指标和医学审计。
6. **旧关系评分器会级联误判。** 把 ICD code/span 纳入端点身份会把一个属性错误传播到中心节点的全部边。
7. **teacher 拥有学生看不到的信息会制造假学习目标。** ICD code 和规范标题必须出现在输入或从目标中移除。
8. **能力较弱的模型不适合不可逆预筛。** 五方对比和后续审计都显示低召回 DROP 会损失高价值文章。
9. **格式有效不等于语义有效。** 标准围栏可本地恢复，但漏关系、语义泛化和实体类型错误无法靠 parser 修复。
10. **同一 prompt 不应无限扩写。** 规则应围绕最常见的正负边界精简增加，过长 prompt 会提高重复 token 成本并干扰模型注意力。
11. **跨来源去重尚未完成。** 当前只在数据库内部去重，因此 252,502 是库内唯一记录数，不一定是跨三库全局唯一摘要数。
12. **全量筛选不是最终知识图谱。** 145,416 篇 KEEP+REVIEW 仍需关系抽取、实体归一、证据验证、冲突处理和图谱级去重。
